## The findings

Each correctness finding that reproduces gets a test in `crates/helm-editor/tests/vim_fixes.rs` that failed on main at `11010ce` and passes with the fix.

1. **`vim.normal` closes the undo group before it finds the buffer unknown** (`editor/vim.rs:493`). Reproduces. `CommandError` says an error changes nothing, but leaving insert mode with an unknown buffer closed the group, so the next typed char started a new undo step. Fix: look up the buffer first. Test: `leaving_insert_mode_with_an_unknown_buffer_keeps_the_group_open`.
2. **A blocked first `u` or `ctrl-r` step still changes the selections and drops goal columns** (`editor/vim.rs:512`). Reproduces. After the step failed, `vim_history` still settled every selection, which drops the goal column `j` set and turns a selection into a cursor. Fix: an error in the first step returns at once. An error in a later step still comes back after the cursors settle, since earlier steps did change things. Test: `a_blocked_first_undo_step_changes_nothing`.
3. **Undo puts the cursor at the selection's start, not where the command acted** (`editor/vim.rs:290` and `:488`). Reproduces. A normal-mode operator, a one-key edit, `o` and `O` act at each selection's settled head, but recorded the selections themselves for undo, so `u` after `x` on the selection `0..4` of `"abc def"` went to offset 0, not 4. Fix: these record a cursor at each settled head. Visual edits still record the visual selection, so `u` goes to where it began, as the `vim` module docs say. The change path normalized the same cursors twice; it now does so once. Tests: `undo_after_an_operator_goes_back_to_the_head`, `undo_after_open_line_goes_back_to_the_head`, and two that pass on main and guard the fix: `undo_after_an_operator_gives_back_settled_cursors` and `undo_after_a_visual_delete_goes_back_to_the_selection_start`.
4. **Three benchmarks time a selection reset** (`benches/vim.rs:188`, `:201`, `:214`). Reproduces: `counted_j_k`, `gg_G` and `counted_dollar` called `editor.set_selections` inside the timed routine. Khakha granted the change proposed on PR #41: the setup builds the editor with `editor_at(&selections)` and the routine returns it, so building and dropping it fall outside the timed code. No other benchmark, id, assertion or budget changes. It is its own commit.
5. **Per-cursor work** (`editor/vim.rs:107`, `motion/vim.rs:385`, `:453`, `:549`, `:697`). A sampling profile of `vim/w_b` put about 60% of its time in the rope's chunk lookup, four per cursor for `w` then `b`. One came from the cursor passes at `editor/vim.rs:107`: every selection was settled in one pass and moved in a second, so each motion looked up the chunk its settle had just read. `vim_move` and `vim_select` now settle and move each selection in one pass, through `vim_start_with`, which hands each selection its goal column. That took `vim/w_b` from 339.84 to 265.31 µs, criterion mean, local. The other sites showed a few percent each and are unchanged. `b` still looks up its chunk twice per cursor, once to settle forward and once to read backward. Sharing the last chunk between the two readers needs `Reads` to borrow from the buffer, a lifetime through every motion function, or a `helm-text` API to re-read a chunk; both are left out.

   The one-pass change slowed `gg` and `G` on CI: `vim/gg_G_1000_cursors_10mb` was 31.28% slower than base on PR #41's head `02a41b9`. A local run from the same benchmark file showed production code caused it, not the finding 4 edit: 155.27 µs with one pass against 127.65 µs with two. `gg` and `G` send every cursor to the same line. With two passes, the second read that line once for all cursors. With one, the read window took turns between each cursor's text and that line. Their target doesn't depend on the cursor (`VimMotion::is_absolute`), so `vim_move` and `vim_select` now find it once, before the pass, and give it to every cursor. Locally `gg_G` then took 112.48 µs, and on CI it was 30.12% faster than base.
6. **`vim/w_b_1000_cursors_10mb` missed its ungated 500 µs target** on PR #38's final head (CI means 606.56, 624.65 and 609.36 µs). With finding 5's changes it meets it. CI run 46009130428 on PR #41's head `e2fdeb6` gave head means of 488.51, 487.76 and 485.58 µs, from the bench job's artifact. Base's means were 609.07, 609.55 and 604.20 µs on the same runner.

   Finding 4 changed the setup of `counted_j_k`, `gg_G` and `counted_dollar`. So CI's base-against-head change for those three mixes the setup edit with code changes, and can't be credited to production code alone. `w_b` doesn't have that problem, since finding 4 didn't change it.
7. **Multiline delete differences** (`motion/vim.rs:647`). Measured against Vim 9.1 (`vim -u NONE -N -i NONE -n -b`) with a scratch harness outside the repo: `d` and `c` with 58 motion and count forms, from random normal-mode cursors, in 20,000 short texts of ASCII lines over the tokens `ab`, `x`, `.`, `a.b`, `cd` and blanks, with no CR. Five kinds of difference, below. Making any of them match Vim changes behaviour the existing tests pin: the oracle in `tests/vim_oracle.rs` models all five for `d`, and a trial patch for the first two failed `d_deletes_the_range_the_oracle_gives` and `every_motion_matches_the_oracle_across_chunks`. Khakha decided on PR #41 to keep all five as listed differences: they are in `vim.rs`'s "Measured against Vim" list, and neither the code nor `tests/vim_oracle.rs` changes.
8. **`editor.rs:642` clones grouped transactions.** Removing the clone may need a `helm-text` API. Left to Stream K; this task doesn't touch `helm-text`.
9. **Two stale sentences in `tasks/108-vim-modes.md`.** Replaced with the wording PR #38's description proposed, in their own commit.
